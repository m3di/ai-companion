# Round 9 — knowledge as an API: modules the day calls, the night maintains

_Planned 2026-07-28. Mehdi's ask: "each one is a module, a set of defined
functions, raw typed code that has documentation and fixed input output … the
session knows what to read and how to run it … the day session should keep all
this information, flaws and nice-to-haves … the night session picks up all the
day session inputs and starts a code audit … no interaction == no improvement,
no friction == code is good."_

## The finding that shapes this round

Round 8 solved STORAGE and left RETRIEVAL untouched. `loadGraph()` reads every
row of every domain to answer anything, the concierge is injected with the whole
tree index every turn, and workers receive the focus set as text. **Context cost
still grows with the size of memory**, which is the ceiling every memory system
eventually hits, and the one thing the JSONL layer was supposed to make
escapable.

The second finding is behavioural, and this session produced four instances of
it. Every rule stated as an INSTRUCTION decayed or was simply wrong — the note
diet ("facts must be timeless") twice, the probe recipe ("small stable output"),
the Fibery `closed_when` vocabulary. Every rule made MECHANICAL held: the
parser, the linter, the round-trip check, the allowlist. The lesson generalizes
past linting:

> If it must hold, it cannot be an instruction.

That decides how friction is captured (below), and it is the difference between
this round working and this round being a nicer prompt.

The third finding is small and blocking: **there is no test suite.** `npm run`
offers `dev`, `start`, `typecheck`. A night session that rewrites functions the
day depends on cannot verify its own work.

## The principle

> Knowledge is an API, not a document. The day CALLS it; the night MAINTAINS it.
> Growth is demand-driven — no friction, no change — and friction is measured,
> never self-reported.

## Design

### 1. Modules

```
data/knowledge/
  <domain>/entities.jsonl        # data (round 8)
  modules/
    entities/
      index.ts                   # exported functions ARE the API
      index.test.ts              # contract tests (required)
      journal.jsonl              # day-written mutations, awaiting the night
```

A module is plain TypeScript: exported functions with JSDoc and concrete types.
No framework, no registration — the catalog is generated by reading the file.

Modules run **out of process** (tsx subprocess, JSON in / JSON out, timeout and
output cap), the same discipline `focus.ts` already applies to probe commands. A
module that hangs or explodes cannot take the bot with it.

### 2. The catalog — what a day agent actually reads

Generated from signatures + JSDoc, injected in place of today's tree index:

```
entities.openLoops(domain?: string): {id, state, actor, blockedBy}[]
  Open entities, optionally scoped to one domain. Cheap.
entities.criticalPath(goal?: string): string[]
  Longest open chain to a goal. Cheap.
entities.find(ref: string): Entity | null
  Resolve an id or alias. Refuses ambiguous aliases.
```

That is the whole change in what an agent sees: **signatures and docs, not
data.** Context per turn becomes a function of the API surface, not of how much
the system remembers.

### 3. Calling, and escaping

- `callModule(module, fn, args)` — the normal path, for workers and concierge.
- `evalInModule(expression)` — Mehdi's "write inline code over module outputs":
  a sandboxed expression with the module namespace in scope, read-only, capped.
  This is what makes composition possible without shipping a function for every
  question anyone might ask.
- Reading the raw source files stays ALLOWED. It has to be — a flaw, a mismatch
  or a missing function must not leave an agent stuck. But see §4: a bypass is
  the single most valuable friction signal we have, so it is recorded.

### 4. The friction ledger — instrumented, not asked for

```sql
friction(id, session_key, kind, module, fn, detail, created_at, resolved_at, resolution)
```

Recorded by the RUNTIME, with no agent cooperation required:

| kind | how it is detected |
|---|---|
| `error` | the module call threw |
| `empty` | the call returned nothing where the caller clearly expected something |
| `slow` | the call exceeded its budget |
| `unknown_fn` | an agent called something not in the catalog |
| `bypass` | **an agent read a raw knowledge file with Read/Grep** |

`bypass` is the important one and it is why this must be mechanical. An agent
that needs something the API cannot give does not file a complaint — it greps
the JSONL and moves on. Dispatch already sees every tool call, so a Read or Grep
under `data/knowledge/` is detectable, and it means exactly one thing: **a
missing function, reported by behaviour instead of by self-assessment.**

Exactly one kind stays agent-reported, because nothing else can know it:
`reportFriction('missing_concept', …)` — the system has no representation for
the thing being asked about at all.

### 4b. The use ledger — added after live testing, and the louder half

The first live session broke the assumption above. Asked which item had been
open longest, the concierge hand-rolled the answer out of two `evalInModule`
expressions — scraping dates out of entity records and message ids — and
answered **confidently and wrongly**: the graph has no creation date, and the
first `msg#` in a chain is when something was first DISCUSSED, not when it
opened. `client-data-import-2420` had been open four months; it reported seven
weeks.

Nothing failed. No error, no empty, no bypass, no `missing_concept` — from the
runtime's side that turn was a clean success. So:

> Instrumenting failure catches an agent that STRUGGLES. It cannot catch one
> that quietly substitutes a plausible proxy, because that agent does not know
> it has a problem.

The signal that does catch it was being thrown away: **an `evalInModule`
expression is a specification written by the caller.** It is work the API made
someone do by hand, in code, and a composition that keeps recurring is a missing
function — by exactly the logic that makes a raw grep one.

```sql
module_use(module, fn, shape, examples, hits, ok_hits, ms_total, first_at, last_at, …)
```

Every call and every expression, not only the failures. `shape` is the dedup
key: a function name for a call, and for an expression the SET OF FUNCTIONS it
touched — composition coalesces far better than wording does, so `find+openLoops`
composed six different ways reads as one missing function stated six times.
Literals are erased before an example is stored, so scoping a query to
"core-api" rather than "paperwork" is not recorded as a different question.

This also supplies §8, which the friction ledger never could: what nothing has
called is a retirement candidate. A function reached through an EXPRESSION
counts as called — the first cut did not credit it, and would have retired the
most-used function in the catalog.

Silent substitution is still not fully solved. The use ledger surfaces the
PATTERN after repetition, not the first wrong answer, and it cannot judge
correctness. That class is found by spot-checking answers against the graph,
which is a human act — worth stating plainly rather than pretending the
instrumentation is complete.

### 5. Mutation discipline

Day sessions may not write knowledge. They may call functions the night marked
`@mutates`, and those append to `journal.jsonl` rather than touching sources.
The night applies the journal in one pass, resolving contradictions jointly —
which is only possible because the writes were batched instead of applied as
they happened.

Scope, per Mehdi: only what is **external, temporal, additive or stateful** —
observations, flags, locks, hit counters, "last seen" marks. Never a fact, never
a relation, never a schema change. Those are the night's.

### 6. Tests, the precondition

`npm test` on `node:test` (in the runtime, no dependency). Three layers:

1. **Invariants** — the round-8 lint rules, the record/row round-trip, the
   simplifier's proofs (reduction removes only implied edges; a critical path is
   a real chain).
2. **Module contracts** — every module ships `index.test.ts`; a module without
   tests is not loadable.
3. **A golden load** — the real tree parses clean and the focus projection is
   non-empty.

The night session runs the suite and **reverts its own work on red.** Without
this, everything in §7 is unverifiable.

### 7. The night: a code audit

A new operator surface, alongside the tree and the ledgers:

1. Read BOTH ledgers since the last pass — friction (§4) and use (§4b). Friction
   alone is not enough: a quiet day of confidently-wrong answers leaves the
   friction ledger empty and the use ledger full, and an audit that reads only
   the first is a no-op exactly when it is most needed.
2. Fix errors. Add the functions that `bypass` rows and RECURRING COMPOSITIONS
   imply — a shape composed by hand more than once is a function. Refactor what
   `slow` rows and high `ms_total` point at.
3. Apply the mutation journal; resolve contradictions across the batch.
4. Run the tests. **Red → revert, and file the failure as friction for tomorrow.**
5. Retire functions nothing has called (§8).

The two halves complete each other without converging: the day only complains
about what it actually hit, so a quiet day produces no change. That is the
design working, not the design idle.

### 8. Decay — the half Mehdi's loop is missing

Friction drives ADDITION; nothing drives REMOVAL, so the module surface grows
monotonically and the catalog becomes the very context cost this round exists to
escape. So: a call counter per function, and the night retires what nothing has
called in weeks — the same treatment "Open possibilities" already gets.

### 9. The boundary (a policy change, made deliberately)

Round 5 made the operator unable to change code: self-modification queues as an
operator-gated PROPOSAL. This round moves that line, and the move is scoped:

- The night session may write **only** under `data/knowledge/modules/`.
- The bot's own source stays proposal-gated, exactly as today.

Memory-layer logic evolves nightly; the machine that runs it does not. Same
boundary as round 5, drawn one level in.

## What round 8 becomes

The first module, and the template for the rest. `entities.jsonl` is its source;
`simplify` / `focusView` / `prober` are its functions, moved out of the bot's
source and into `modules/entities/`. Nothing is discarded — the round-8 work is
what proves the shape before any second module exists.

## Sequencing

Each step is only safe after the one before it:

1. **Test harness** — nothing else can be verified without it.
2. **Friction instrumentation** — mechanical; starts accumulating immediately.
3. **Module runtime + catalog + `callModule`** — the day stops reading data.
4. **Port the entity graph to `modules/entities/`** — the template.
5. **Night code audit** — only once 1–4 exist and there is real friction to act on.

Steps 3–5 do not pay off at 153 entities: the graph still fits in a prompt. They
are worth starting now because **friction data takes calendar time to
accumulate**, and instrumenting early is what makes the night's first audit
evidence-driven instead of speculative.

## Risks worth stating

- **Agent-written code breaks retrieval for every agent.** Mitigated by tests as
  a hard gate, out-of-process execution, and the `modules/` boundary — not
  eliminated.
- **Friction noise.** A flapping probe taught round 7 to cap escalations; the
  same governor belongs here, or one broken function floods the ledger and
  drowns the signal.
- **Premature abstraction.** Genuinely possible. The defence is that the module
  surface is demand-driven: if nothing complains, nothing gets built, and the
  cost of the machinery is one runtime plus a catalog.
- **The catalog becoming the new context tax.** Watched by §8, and worth an
  explicit budget line the way `root.md` has one.

## Explicitly NOT doing

- **Python.** JSONL keeps it open for a future analysis layer; `tsc` is the
  compiler this round needs, and accessors that run in-process beat a subprocess
  boundary for every read. Revisit only if real numeric work (matrices,
  statistics over a large corpus) becomes the point.
- **Free-form code execution outside the module sandbox.**
- **The night session touching the bot's own source.**
- **Building a module per domain up front.** One module, then let the complaints
  choose the second. Building eleven modules nobody has called is the exact
  failure "no friction, no improvement" is designed to prevent.
